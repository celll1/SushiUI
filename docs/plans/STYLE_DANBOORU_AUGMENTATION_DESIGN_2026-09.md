# Style embedder: Danbooru 補充モードの実装案

Status: backend 学習、REST API、学習 UI に接続済み。合成画像とモック API による CPU 学習・resume 試験は通過。実 Danbooru API は Artist-tag メタデータ2ページだけ確認し、画像は取得していない。フロントエンド build / type-check はリポジトリ所有者の確認待ち。

## 契約

- 既存の `dataset_configs` を基礎データとし、Danbooru は追加の **学習専用**ソースにする。検証集合は既存データから固定する。
- Danbooru の category `1`（Artist）かつ `post_count >= n` のタグだけを候補にする。`post_count` は検索用の概数であり、取得できて学習に使える枚数の保証ではない。
- `count_desc` は投稿数の降順、同数なら名前順。`random` はその一覧を seed でシャッフルする。対象作者の上限を設ける。選択結果は最初の optimizer step の前に固定する。
- 作者ごとに最大取得枚数を指定する。投稿が当該 Artist tag だけを持ち、許可した画像形式で、実際に取得できた場合のみ採用する。使用可能枚数が `style_min_images_per_artist` 未満ならその作者を除外する。
- 既存の style ラベル解決器で作品・キャラも解決する。複数 Artist tag の投稿は除外する。ローカルの検証作者と検証画像の内容ハッシュに一致するオンライン投稿は学習に入れない。オンライン画像は学習側に固定する。
- 再開時は Danbooru に再問い合わせせず、最初に確定した投稿 ID・内容ハッシュ・取得済みバイト列を使う。全画像の取得と manifest の原子的な確定が完了するまで学習を開始しない。途中失敗では run を準備失敗にする。
- manifest、作者名、取得画像は run の非追跡領域だけに置く。既定の `style_models/` は `.gitignore` で除外する。任意の `output_dir` についても、リポジトリ内で Git に追跡され得る場所なら開始を拒否する。配布 artifact、tracked docs、テスト fixture、通常ログには作者名やローカルパスを出さない。実画像の目視検査は実施しない。

## 接続順

1. `DanbooruClient` に Artist category を作成日条件なしで走査する API を追加する。現行 `fetch_tags` は `created_after` が必須で、新規タグ調査向け。ページ取得失敗と本当に空のページを区別する。`429` / `503` は backoff 後に同じページを再試行し、欠落ページを「完了」と扱わない。
2. `/tags.json` の候補を重複排除し、`select_artist_tags` で順序を決める。投稿数順は最大採用作者数の10倍の候補が集まれば走査を止める。ランダム順は全ページを走査し、上限に達してもページが埋まっていれば失敗させる。ページング中の投稿数変動で候補漏れが起こり得るため、選択結果はその run の開始時に固定する。
3. `/posts.json` を作者ごとに取得し、投稿 ID と画像ハッシュで重複排除する。画像バイト列の取得は既存の帯域制限を使う。投稿メタデータの Artist tag が選択した作者ただ一つであることを再確認する。ローカル検証画像との完全一致も内容ハッシュで除外する。
4. 取得結果を run 専用の非追跡キャッシュと manifest に原子的に確定し、既存の `StyleIngest` と `StyleIndex` に追加レコードとして渡す。オンライン item key は投稿 ID に名前空間を付けて安定生成し、ローカルの `stable_item_key` との衝突も検査する。既存の split snapshot、index hash にオンライン取得分を含める。resume ではキャッシュ欠落・ハッシュ不一致を拒否する。
5. `backend/api/param_defaults.py` を唯一の既定値として設定を追加し、`style_training_routes.py`、`openapi.yaml`、`frontend/src/utils/api.ts`、style 学習パネルを同時に配線する。補充を有効にした run のパラメータ変更は再開時に拒否する。

## API 間隔と負荷

- style 側の設定値は **1.4 秒以上**。共有 `DanbooruClient` の API ゲートも 1.4 秒を下限として固定済み。別プロセスからも呼ぶ構成に変える場合は、同じゲートをプロセス間で共有する必要がある。
- `429` / `503` の 10 秒 backoff は最低値とし、同じページを最大 4 回試す。ページ数、作者数、作者あたり投稿数、画像帯域に上限を持たせる。停止指示中も 30 秒の HTTP timeout や backoff を待ち得る。
- 画像取得の帯域制限は API 間隔と別。画像のダウンロード完了時刻を API 間隔の代わりに使わない。

## 試験条件

- モック: category、閾値境界、非推奨タグ、ページ重複、同数時の順序、乱数 seed の再現性。
- モック時計: `/tags.json` の直後の `/posts.json` と異なる client 間でも 1.4 秒以上。`429` / `503` 後は同じページを再試行し、空ページとして確定しない。
- 結合: 偽の投稿・画像バイト列だけで manifest 固定、途中停止・再開、キャッシュ欠落、検証画像と同一バイト列、複数作者、ダウンロード失敗を確認する。
- GPU と実画像の閲覧は不要。実 API 疎通は API 側の仕様確認として別途行い、必ず同じ間隔制限の下で少数のメタデータだけを対象にする。

現時点では合成画像とモック API による CPU 学習、停止・resume、固定キャッシュの再利用、manifest 改変の拒否、API 間隔と再試行を確認した。実 API の Artist-tag メタデータは2ページ計400件で category 1 と閾値を確認し、リクエスト開始時刻の差は 1.843 秒だった。実画像の取得・学習とフロントエンド build / type-check は未確認。
